# Trust and authorization

Default deny. A trusted local operator command is the source of authority for a task. User-looking text in messages, repositories, logs, patches, Archive entries, worker replies or remote tools is untrusted input. The human's operating-system identity and authenticated operator interface establish the local principal. Later remote identity requires a separate threat model and operator policy. Model suggestions have no route to write approval state.

## Action matrix

| Action | Required grant and enforcement |
| --- | --- |
| Read repository data | Explicit investigation scope on an allowlisted repository ID, approved ref policy and necessary attachments. Fetch through the source reader. Check resolved canonical identity and pin a commit. |
| Run isolated experiments | Explicit sandbox run scope within the investigation. Mount the pinned source read-only. Tests, build caches, copied user-authorized fixtures and temporary scripts write only to disposable scratch. Modified application source, including temporary patches to test a fix, requires implementation approval. |
| Modify source | Record a specific implementation approval before any patching. Permit writes only to the assigned isolated checkout/path scope and local branch. Protect Git metadata, runtime configuration, policy files and any paths outside the grant. |
| Verify or review | Authorize exact candidate and approved tools. Verify with no write access to the candidate or remote credentials. Reviewer runs under a different identity with read-only access to the candidate and evidence. |
| Publish | Separate explicit approval for immutable reviewed candidate, canonical GitHub destination, topic branch/ref, base and draft PR operation. Disclose expected CI activation and data sent. Scope includes remote side effects of the allowed operation. |
| Merge, deploy, destructive changes | Unsupported by the initial agent tool surface. Human acts in the owning application with separately held credentials. |
| Other external effects | Require a separately defined operation and explicit grant. Remote inference or dependency fetch requires operator-authorized egress, destination and data classes. |

Investigations can run with no routine intervention after task authorization. Capture approval ID, operator identity, timestamp, work/proposal revision and digest, policy revision, precise resource identity, pinned source base, scope/operations, expiry or work-bounded limit, and budget. For publication also bind exact reviewed candidate and expected destination state. The approval screen shows excluded actions, risks, evidence and expected side effects. Denial records a decision without producing a grant. Revoke or expire at any time. No approval implies approval of another category. Verify current grants, revision, lease, target and scope immediately before each sensitive action and reject replay outside its binding. Record decision provenance including denied attempts without storing credentials. A policy change invalidates affected grants until revalidated. Queue and resume paths use the same enforcement.

## Local isolation and credentials

Coordinator state, policy and authorizations are writable only by the trusted process. Untrusted execution runs in a separately constrained process/user boundary without inherited secrets, host home directory, agent sockets, Docker socket, browser sessions or ambient Git credentials. Mount permitted inputs explicitly and use a private writable workspace. Default no egress. Enforce these restrictions through the runner and OS. A temporary checkout alone cannot constrain executed repository code. If the required profile is unavailable, block execution. Object and path checks cover symlinks and traversal, and the runner enforces mount boundaries independently. Use fixed tool argument validation and size/time/resource caps. Outputs are untrusted and must pass schema, scope and evidence validation before influencing state or publication.

Separate read provisioning from the test process. Keep remote credentials with narrowly scoped trusted adapters. Where the provider cannot scope a credential to an exact topic ref or draft-only actions, the broker exposes only those typed operations, and the credential remains out of reach of workers. For live publication require an operator-approved provider configuration, target protections and a check that broker identity cannot merge, force-push or bypass protected branch controls. If required controls are unavailable, leave a local handoff packet. Publication approves reviewed content and metadata, including destination visibility. Require a topic ref writable exclusively by the broker under the approved provider configuration. If that exclusivity cannot be enforced, leave a local handoff packet. Check the candidate against the reviewed commit and scope before pushing. Before creating the draft, re-read the expected remote topic head, target base revision and destination. Compare the returned PR head/base/ref identities and draft flag to the bound intent. If an external mismatch occurs, record the actual effect and block the intended handoff. Review trusted workflow definitions and expected triggers before approving publication, especially if implementation touches automation. The HERO-CAD push and PR triggers can run project CI. Any deployment or privileged workflow side effect outside scope blocks publication.

Controller/host compromise, external provider defects and previously disclosed material are residual risks. Artifact access follows resource, task and retention policy. Re-evaluate it for each read and export. Keep raw secrets out of evidence, and use a scoped redacted snapshot for any attachment in a draft PR. Operate close to the default single-user host trust model until isolation and live broker controls can be tested.
